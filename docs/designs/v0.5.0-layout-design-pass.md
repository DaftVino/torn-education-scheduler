# v0.5.0 — the layout design pass

**Status:** ready to run. Nothing here is implemented.
**Date:** 2026-08-05
**Baseline:** v0.4.0, tagged. The design tokens have shipped, so the baseline
these mockups are drawn against is stable — which is the precondition
`v0.3.0-color-tokens.md` set for running this round at all.

## What this is

The mockup round specified in `v0.3.0-color-tokens.md` § "The remaining design
work", scoped to the layout questions a stylesheet cannot answer. It was
specified before v0.4.0 and skipped; this document is it, narrowed to what is
still open and widened by what the v0.4.0 QA gate exposed.

**It also absorbs `v0.2.0-scope.md` § J2, the "usability design pass"** (merged
here by the owner, 2026-08-05). § J2 predated this document and asked for the
same thing in vaguer terms — a deliberate pass over the whole UI for clarity,
after v0.1.0 shipped the minimum styling needed to be legible. Two documents
asking for one design round is how a round gets run twice or not at all, so
§ J2 is now a pointer here and this file is the only live design scope.

The one thing § J2 carried that the token round did not, and which survives as
this round's tie-breaker:

> **Usability over presentation. Clean and clear beats attractive.**

Apply that when a comparison board offers a prettier direction and a plainer
one. It is the owner's stated priority, not a preference to re-derive.

**Run it with `/plan-design-review`** — the gstack designer, a comparison
board, pick a direction. Layout questions need pictures. That is the whole
reason this is a separate round rather than four more bullet points in a
correction plan.

## Why it is worth running, stated plainly

The v0.4.0 gate answered the Focus view's layout through eight rounds of
browser QA, one owner instruction at a time. The result is good. The cost was
three build–test–look cycles and a QA checklist that went stale twice while the
screen moved underneath it.

That is the argument for this round, and it is the only argument being made
here: **a comparison board is cheaper than an iteration**, because a picture
can be rejected before anything is built. It is not an argument that the
current screens are wrong.

## Question 1 — the degrees grid

**Today:** thirteen bordered cards, `repeat(auto-fill, minmax(160px, 1fr))`,
each holding a category name, a course count, a duration and a finish date.

**The question:** should read-only figures be cards at all? Under App-UI rules
a card earns its existence by being the interaction. These are not interactive
— nothing in the grid is clickable. A compact table may read better and denser,
and would let the thirteen finish dates line up in a column where they can
actually be compared, which is the comparison the screen exists to support.

**Evidence for the board:**

- The all-remaining box was already pulled out into a full-width banner
  (`.tes-all-banner`) because a box among boxes read as a fourteenth degree
  rather than the total. That is the same instinct applied to one cell, and it
  worked — which is weak evidence that the card treatment was carrying less
  than it looked like it was.
- The panel sits inside Torn's own column, whose width the script does not
  control. Any direction must survive a narrow column; that is why the current
  grid uses `auto-fill` rather than a fixed column count.

**Directions worth boarding:** the current cards; a compact table with
right-aligned dates; a two-column definition list.

## Question 2 — the queue row

**Today:** two lines in a CSS grid — the course line, then an indented smaller
bonus line — with the remove button spanning both rows in column 2.

**The question:** does that read as one item or as two? It shipped as specified
and has never been reviewed as a picture. The spanning button was chosen so the
button could not double or drift from the row it belongs to; whether the
resulting block reads as a single queue entry is exactly the thing prose cannot
settle.

**Constraint any direction must hold:** a course name comes from Torn and can
be long. The current layout absorbs that in the `1fr` track. A direction that
puts the bonus text on the same line as the name has to say what happens at 115
queued courses with names of unbounded length.

## Question 3 — the Focus view — CLOSED, do not re-board

Answered during the v0.4.0 QA gate. Recorded here so this round does not
re-open a screen the owner has already iterated to where they want it:

- Priority control lives in the section header, in a fixed-width slot, so
  choosing a selection does not shift the header text. It is a **sibling** of
  the toggle button, never a descendant — an `<input>` inside a `<button>` is
  invalid, and a click on the number would collapse the section being
  renumbered.
- Category sections are outlined cards, collapsed by default, matching the
  degrees cards' border.
- Each header carries the chosen selection's name and a right-aligned
  `X rem /X total` count, readable with everything collapsed.
- Completed-and-unchosen selections gather into a nested collapsed `completed`
  group at the foot of their category. A completed selection that **is** chosen
  stays in the main list, because its checkbox is the only control that can
  untick it.

**If this round has an opinion about the Focus view, it is out of scope.**

## New since the original spec

Two things the v0.4.0 gate produced that this round should look at, because
neither has ever been seen as a picture:

1. **The schedule's boosters block is now four stacked lines of prose** — a job
   points line, a planned Books line, a floor line with its cost, and a caveat
   sentence — rendered as one `pre-line` text node. It grew a line per feature
   and has never been designed. The information is load-bearing (the floor date
   must never appear without its cost), so this is a question about presenting
   a small table, not about cutting content.
2. **Settings is now five sections** — Boosters, Planning, Help, "Recorded with
   this plan — not calculated", Share this plan. The fourth title is doing
   copywriting work that a layout might do better.

## Out of scope

- Any change to what the panel computes. This round moves pixels.
- The Focus view (question 3, closed above).
- The colour, type and spacing tokens. They shipped and
  `tests/style.test.js` polices them: no hex outside the token block, every
  declared token referenced and every referenced token declared, no literal
  `px` in `font-size`/`margin*` outside the token block, no `opacity`, no
  `color-mix`, no plain `:focus`. **A direction that needs a new token must say
  so explicitly** — it is not a free move.

## Definition of done for this round

A comparison board per open question, a chosen direction per question, and an
implementation plan. **Not** an implementation: the ordering rule that got
skipped last time is that the pictures come before the build.
