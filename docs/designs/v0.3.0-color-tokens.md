# v0.3.0 § H6 — Design tokens

**Status:** spec, ready to plan. **Sequenced last — see "This goes last".**
**Date:** 2026-08-04
**Source:** `X:\Projects\Torn Bookie Live Scores`, default ("Default Dark")
scheme, `Torn_Bookie_Live_Scores.js:8244-8277`.
**Scope widened by design review, 2026-08-04** — see "Design review findings".
This began as colour only; the review found that colour is the *least* of what
the panel is missing, and that three more token families cost a handful of CSS
lines each while improving every screen at once.

## What this is

Replace every hardcoded value in the panel's stylesheet with a CSS custom
property: **colour** (from Torn Bookie Live Scores' default scheme), plus a
**type scale**, a **spacing scale**, and a **focus ring**. One theme only.
**No theme switcher**, no stored theme preference, no settings control — this
is a refactor of how the panel's visual decisions are expressed, not a feature.

`CLAUDE.md` already says the panel is "modelled on Torn Bookie Live Scores".
Today that resemblance is by eye and by accident. Tokens make it structural, so
the two panels drift together instead of apart, and so a future theme is a
change of values rather than a rewrite of rules.

## This goes last

**Implement only after § H3 (focus mode), § H4 (reset controls) and § H5 (UI
corrections) have landed.**

Each of those adds new styled elements: a focus view with per-selection rows,
an armed-state reset button in a warning colour, a header toggle button, an
all-remaining banner, a structured schedule summary with a separator border,
and a green bachelor option. Tokenising first means tokenising again for every
one of them, and worse, it means three specs choosing hardcoded colours that a
fourth then has to hunt down. Going last, this pass sees the finished surface
once.

**§ H5 item 8 is the specific coupling.** It introduces `#7ee081` as an
`<option>` colour by naming the literal. When this spec runs, that literal
becomes a token — so H5 must not be written in a way that makes the hex hard to
find. One occurrence, in the stylesheet, is fine.

## The source has two different "defaults"

Bookie declares the default scheme twice, with values that disagree:

| Token | Panel root (`:8245`) | `.tm-theme-default` (`:10077`) |
| --- | --- | --- |
| `--tm-text` | `#ffffff` | `#e0e0e0` |
| `--tm-accent` | `#cc0000` (red) | `#6ea3d0` (blue) |
| `--tm-good` | `#2a6b3a` | `#5dba6d` |
| `--tm-bad` | `#a33` | `#e06060` |
| `--tm-border` | `#3a3a3a` | `#333` |
| `--tm-bg-4` | `#191919` | `#2f2f2f` |
| `--tm-hover` | `#292929` | `#333` |

**The panel root is canonical here.** It styles Bookie's main floating panel,
which is the thing this project's panel is modelled on; `.tm-bookie-details` is
a nested detail component with its own local palette. Adopting the details
palette would copy a sub-component's overrides and call them the house style.

This disagreement is a finding about the source, not about this project. It is
recorded here so the next person does not "fix" our tokens to match the other
block. **Worth reporting upstream to the Bookie repo** — two blocks both
claiming to be the default is a bug there whichever one is right.

## The green does not survive the move, and neither do the red or the accent

Bookie uses `--tm-good`, `--tm-bad` and `--tm-accent` predominantly as fills,
borders and badges. This panel uses green and red as **text** — the finish date
line and the error line are coloured type on a dark background. Measured
against `--tm-bg` (`#1f1f1f`):

| Token | Value | As text on `--tm-bg` | WCAG AA (4.5:1) |
| --- | --- | --- | --- |
| `--tm-good` | `#2a6b3a` | **2.56:1** | ✗ fail |
| `--tm-bad` | `#a33` | **2.54:1** | ✗ fail |
| `--tm-accent` | `#cc0000` | **2.80:1** | ✗ fail |
| `--tm-warn` | `#ffcc00` | 10.90:1 | ✓ |
| `--tm-text` | `#ffffff` | 16.48:1 | ✓ |
| `--tm-muted` | `#b8b8b8` | 8.31:1 | ✓ |
| `--tm-meta` | `#cfcfcf` | 10.58:1 | ✓ |

What the panel uses today:

| Current | Role | On `#1c1c1c` |
| --- | --- | --- |
| `#7ee081` | `.tes-finish` — the number this tool exists to produce | **10.44:1** |
| `#e6e6e6` | body text | 13.65:1 |
| `#ff8080` | `.tes-save-error`, `.tes-error` | 7.02:1 |

**Naively adopting `--tm-good` for the finish date takes it from 10.44:1 to
2.56:1** — a fourfold contrast regression on the single most important line in
the panel, and a failure of the one accessibility bar that has a number
attached to it.

So the token set gains three text-safe siblings, and the rule is explicit:

```css
--tm-good: #2a6b3a;          /* fills, borders, badges — Bookie's value, unchanged */
--tm-good-text: #7ee081;     /* coloured type on --tm-bg — this panel's existing green */
--tm-bad: #a33;              /* fills, borders */
--tm-bad-text: #ff8080;      /* coloured type — this panel's existing red */
--tm-accent-text: #6ea3d0;   /* if accent is ever needed as type */
```

`--tm-good-text` and `--tm-bad-text` keep the panel's current values precisely
because those values already pass. **The visible result of this entire spec
should be no visible change**, which is the strongest evidence a token refactor
did what it claimed.

The naming carries the rule: a token ending `-text` is for type, one without is
not. A reviewer seeing `color: var(--tm-good)` knows it is wrong without
measuring anything.

## Design review findings

**Nothing in this section has been implemented.** The review ran against the
stylesheet and the four v0.3.0 specs and produced findings; no CSS was changed
and no mockup was generated. Both halves of the design work below — the
high-ROI pass and the mockup round — are **specified, ordered, and waiting**,
by the owner's decision on 2026-08-04. This section is the record of what to
do and in what order, not a report of work done.

`/plan-design-review`, 2026-08-04, scoped by the owner to the whole panel
rather than only the new work, optimising for visual payoff per unit of effort.
**Initial rating: 4/10 on design completeness.** Not because the specs are
vague — they are unusually precise about behaviour — but because all four
specify behaviour and none specifies a visual system.

Measured against the current stylesheet (26 rules):

- **One font size for the whole panel.** `font-size: 13px`, with `1.25em` on
  exactly one element. That is the entire type hierarchy.
- **One spacing value.** `margin-bottom: 8px`, repeated eleven times. Nothing
  groups visually because everything is equally far from everything else.
- **Hierarchy is done with `opacity`** — `0.85`, `0.75`, `0.7` on
  `.tes-section-title`, `.tes-note`, `.tes-cell-detail` and `.tes-foot`. This
  is why the panel reads washed rather than layered: opacity dims text against
  whatever happens to be behind it, where a muted colour is a deliberate step
  with a known contrast ratio.
- **Zero focus styles.** No `:focus`, no `:focus-visible`, anywhere. A keyboard
  user cannot see where they are — on a panel about to gain a Focus view full
  of checkboxes and number inputs, and a two-click reset whose armed state is
  invisible without a visible focus.
- **13px body text; buttons about 26px tall** (`padding: 4px 8px` at 13px).
  Both under the usual floors of 16px body and 44px touch target.

The four fixes below are the whole of the high-ROI pass. Each is a few lines,
each is a token, and each improves every existing screen and every screen H3,
H4 and H5 add.

### 1. Type scale — three steps

```css
--tes-text-sm: 12px;    /* meta, notes, cell detail, the H5 bonus line */
--tes-text: 14px;       /* body — up from 13px */
--tes-text-lg: 1.25em;  /* .tes-finish, unchanged */
```

14px rather than 13px because this is dense utility UI where 16px would cost
real rows, but 13px is below the floor with no compensating benefit. The H5
bonus line (item 4, "smaller font indented below") resolves to `--tes-text-sm`
rather than inventing a fourth size.

### 2. Spacing scale — four steps

```css
--tes-gap-xs: 4px;
--tes-gap-sm: 6px;
--tes-gap: 8px;
--tes-gap-lg: 14px;   /* between sections — the step that does the grouping */
```

Eleven identical `margin-bottom: 8px` declarations become a scale. The one that
matters is `--tes-gap-lg`: sections currently sit the same distance apart as
the rows inside them, so the panel has no visible grouping. This single step is
the largest perceived-polish change in the whole spec, and it is one value.

### 3. Retire `opacity` for text hierarchy

| Rule | Today | Becomes |
| --- | --- | --- |
| `.tes-section-title` | `opacity: 0.85` | `color: var(--tm-meta)` |
| `.tes-note` | `opacity: 0.75` | `color: var(--tm-muted)` |
| `.tes-cell-detail` | `opacity: 0.85` | `color: var(--tm-meta)` |
| `.tes-foot` | `opacity: 0.7` | `color: var(--tm-muted)` |

`--tm-meta` (`#cfcfcf`) and `--tm-muted` (`#b8b8b8`) measure 10.58:1 and 8.31:1
against `--tm-bg`. The opacity values they replace produce whatever they
produce. Same intent, known result.

### 4. A visible focus ring

```css
--tes-focus-ring: 2px solid var(--tm-good-text);

#tes-panel button:focus-visible,
#tes-panel select:focus-visible,
#tes-panel input:focus-visible,
#tes-panel textarea:focus-visible { outline: var(--tes-focus-ring); outline-offset: 2px; }
```

`:focus-visible` rather than `:focus` so a mouse click does not leave a ring
behind. This is the only item here that fixes a defect rather than an
aesthetic: today, tabbing through the settings form gives no indication of
position at all.

### Do NOT adopt `--tm-font`

The original draft of this spec proposed `--tm-font: Arial, Helvetica,
sans-serif`, copied from Bookie. **Dropped.** The panel sets no font for its
text and inherits Torn's, which is exactly why it looks like part of the page it
lives in rather than something bolted on. Adopting a default stack would be
strictly worse *and* more work than doing nothing.

**Corrected 2026-08-05, found during implementation.** An earlier draft of this
section claimed the panel "sets no font" at all. That is false: `.tes-share`
declares `font-family: monospace`. It is a **deliberate exemption and stays** —
the share box holds a machine-readable token the player copies and pastes, where
monospace makes the string legible and its boundaries unambiguous. That is a
functional choice about one control, not a typographic identity choice about the
panel, and the rule here was only ever aimed at the latter.

So the rule, stated precisely: **no `--tm-font` token, and no `font-family` on
the panel root.** A root declaration is what would override Torn's inherited
font for every piece of text in the panel; a `font-family` on a single
purpose-built control is not the same thing and is not forbidden. The test in
`tests/style.test.js` asserts the narrow rule, not the blanket one — a blanket
assertion could never have passed, and would have pressured whoever met it into
deleting a monospace declaration that is doing real work.

`--tm-font` is therefore in the "not adopted" list below, and the reason is
recorded because "Bookie has it and we don't" looks like an oversight
otherwise. **Agreed by the owner, 2026-08-04.** The panel sets no font family
and there is no font token; this is settled, not deferred.

### Accessibility floors this establishes

- Body text `--tes-text` (14px) minimum; `--tes-text-sm` (12px) only for
  genuinely secondary content, never for a value the player must act on.
- Every interactive element reaches 44px of touch target, via padding rather
  than font size. Buttons go to `padding: 8px 12px`.
- Every `-text` colour token clears 4.5:1 against `--tm-bg`, already asserted.
- Focus is visible on every interactive element.

## The remaining design work, and how to run it

The four fixes above are the high-ROI pass and are specified. **What they do
not settle is whether the panel's layout is right** — three questions the
review surfaced and could not answer from a stylesheet:

1. **The degrees grid is thirteen bordered cards** (`repeat(auto-fill,
   minmax(160px, 1fr))`). Under App-UI rules a card should earn its existence
   by being the interaction; these are read-only figures, and a compact table
   may read better and denser. H5 item 6 already pulls the all-remaining box
   out as a banner, which is the same instinct applied to one cell.
2. **The queue row becomes two lines with a spanning remove button** (H5 item
   4). Whether that reads as one item or two is a layout question.
3. **The Focus view has no layout at all yet** — ten categories, 79 selections,
   priority numbers, and per-selection remaining figures. It is the densest
   screen in the panel and the only one designed entirely in prose.

**Order of work, when this is built:**

1. **The high-ROI pass** — the four token fixes above. First, because it
   changes every screen's baseline, and mocking up a baseline that is about to
   change would throw the mockups away.
2. **Then the mockup round** — `/plan-design-review` with the gstack designer,
   comparison board, pick a direction, for the three layout questions above and
   nothing else. Layout questions need pictures; the four token fixes did not.

Neither step has been run. The order is the point of recording it: doing them
the other way round wastes the mockups, and it is not obvious from either
step's own description.

## Token set

Adopted from the panel root block, verbatim unless noted:

```css
#tes-panel {
  --tm-bg: #1f1f1f;
  --tm-bg-2: #242424;
  --tm-bg-3: #111111;
  --tm-bg-4: #191919;
  --tm-hover: #292929;
  --tm-border: #3a3a3a;
  --tm-border-2: #555555;
  --tm-text: #ffffff;
  --tm-muted: #b8b8b8;
  --tm-meta: #cfcfcf;
  --tm-accent: #cc0000;
  --tm-warn: #ffcc00;
  --tm-good: #2a6b3a;
  --tm-bad: #a33;
  --tm-good-text: #7ee081;    /* added — see above */
  --tm-bad-text: #ff8080;     /* added */
  --tm-accent-text: #6ea3d0;  /* added */
  --tm-focus: var(--tm-accent);

  /* Type — three steps, review finding 1 */
  --tes-text-sm: 12px;
  --tes-text: 14px;
  --tes-text-lg: 1.25em;

  /* Spacing — four steps, review finding 2 */
  --tes-gap-xs: 4px;
  --tes-gap-sm: 6px;
  --tes-gap: 8px;
  --tes-gap-lg: 14px;

  /* Focus — review finding 4 */
  --tes-focus-ring: 2px solid var(--tm-good-text);
}
```

**Not adopted:** `--tm-card-*` (no card surface here), `--tm-source-*` (score
providers, meaningless in this project), `--tm-success/-info/-warning/-danger`
and their `-bg` pairs, and `--tm-game-*`. Carrying tokens nothing references
makes the set look like a design system and behave like dead code.

**`--tm-font` is not adopted**, and this is a decision rather than an omission:
the panel inherits Torn's font, which is what makes it look native to the page.
See the review finding above. Owner-agreed 2026-08-04.

The `--tes-*` prefix on type, spacing and focus is deliberate: `--tm-*` names
mean "this value came from Bookie and matches it". Type and spacing did not
come from Bookie and do not match it, so borrowing its prefix would claim a
provenance they do not have.

**`color-mix()` is not adopted.** Bookie derives its `-bg` variants with
`color-mix(in srgb, …)`. Nothing here needs a translucent fill today, and
adding an unused dependency on a newer CSS function for the pleasure of
symmetry is the kind of thing this repo does not do.

## Mapping

Every hardcoded colour currently in the stylesheet:

| Current | Becomes | Note |
| --- | --- | --- |
| `#1c1c1c` panel background | `var(--tm-bg)` | `#1f1f1f`, a hair lighter |
| `#4a4a4a` panel and button borders | `var(--tm-border-2)` | `#555555` |
| `#e6e6e6` body and button text | `var(--tm-text)` | `#ffffff` |
| `#2e2e2e` button background | `var(--tm-hover)` | `#292929` |
| `#7ee081` `.tes-finish` | `var(--tm-good-text)` | unchanged value |
| `#7ee081` button `:hover` border | `var(--tm-good-text)` | unchanged value |
| `#ff8080` `.tes-save-error`, `.tes-error` | `var(--tm-bad-text)` | unchanged value |
| Arial stack, wherever inherited | `var(--tm-font)` | |

Four background and border values shift by a few points of luminance. That is
the whole visible delta, and it is the point: the panel adopts Bookie's greys
exactly rather than approximately.

Elements added by H3/H4/H5 are tokenised in the same pass, against the same
table. Anything they introduced that has no token gets one here rather than
staying a literal.

## Rules this establishes

1. **No hex literal outside the token block.** One place declares colour.
2. **`-text` tokens for type, plain tokens for fills.** Never `color:
   var(--tm-good)`.
3. **Any new coloured type meets 4.5:1 against `--tm-bg`**, measured, not
   judged by eye.
4. **Token values come from Bookie's panel root**, not from
   `.tm-theme-default`, and not invented here. The three `-text` additions are
   the only local values, and each exists because a Bookie token failed a
   contrast measurement.

## Behaviour

| Condition | Behaviour |
| --- | --- |
| Panel renders normally | Visually near-identical to today; only greys shift |
| A browser without CSS custom property support | Not supported — custom properties are universal in any browser Tampermonkey runs on. No fallback declarations |
| Torn's own page CSS declares `--tm-*` | Scoped to `#tes-panel`, so the panel's declaration wins for its own subtree |
| A future theme is wanted | Change values on the `#tes-panel` block. Out of scope here |

## Testing

Styles are a string in this codebase, so they are testable as one.

1. Assert the stylesheet contains **no hex colour literal outside** the token
   block — a regex over the emitted CSS string. This is the test that keeps
   rule 1 true after this session ends.
2. Assert every `--tm-*` token declared is referenced at least once, and every
   `var(--tm-*)` referenced is declared. Both directions: an undeclared token
   renders as nothing, and an unreferenced one is dead weight.
3. Assert `.tes-finish` resolves to `--tm-good-text`, not `--tm-good`.
4. Assert `.tes-save-error` and `.tes-error` resolve to `--tm-bad-text`.
5. A contrast test with the ratio computed in the test itself, asserting every
   `-text` token clears 4.5:1 against `--tm-bg`. Hardcoding the expected ratios
   would let a token change silently break the thing the test exists to
   protect.
6. Assert no `color-mix(` appears in the stylesheet.
7. Assert the token block is scoped to `#tes-panel` and nothing is declared on
   `:root` — the panel must not leak variables into Torn's page.
8. Assert the stylesheet declares **no `font-family` at all**. This is the test
   that keeps the owner's decision true; without it, a future session adds
   `--tm-font` back as "consistency with Bookie" and nobody remembers why not.
9. Assert **no `opacity:` appears on a text rule** — the four opacity-based
   hierarchy steps are gone and cannot creep back.
10. Assert a `:focus-visible` rule exists covering `button`, `select`, `input`
    and `textarea`. Absence of a focus ring is invisible in every screenshot and
    in every review that does not press Tab, so it needs a test rather than an
    eye.
11. Assert no literal `px` font size or margin outside the token block — the
    same rule as hex literals, applied to the two scales.

## Open questions

- **Does the owner want `--tm-bg` (`#1f1f1f`) or to keep `#1c1c1c`?** Adopting
  Bookie's value is the point of the exercise, but it is a real, if small,
  visible change to a panel that has shipped. This spec adopts it.
- **Report the duplicate default upstream?** The two disagreeing blocks in
  Bookie are a defect there. Worth an issue on that repo.

## What this does not change

- Any behaviour, any arithmetic, any stored data.
- The security surface: no new grant, no network, no storage key.
- Zero dependencies, no build step.
- Layout, spacing, typography scale, or any element's structure — colour only.
