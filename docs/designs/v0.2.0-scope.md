# v0.2.0 scope and remaining work

Date: 2026-08-04
Status: scope, not yet a plan. Nothing here has been brainstormed or planned.

This is the single home for every piece of work not shipped in v0.1.0. It exists
because the v0.1.0 execution ledger — which tracked deferred and parked findings
during the build — was deleted when that work merged, and several items lived
only there. Anything not written down here is lost.

Precedence: where this document and
`docs/superpowers/specs/2026-08-03-torn-education-scheduler-design.md` disagree,
**this document is current**. The design doc describes the intended system; the
divergences below record where the shipped code does not match it yet.

## What v0.1.0 actually shipped

Recorded because the design's release table claimed some of this for v0.2.0.

- Reads `page.php?sid=educationInitData` with the `rfcv` anti-CSRF token.
- Adding a course queues its full prerequisite chain, dependency-ordered.
- Exact finish date and time, plus a projected finish per queued course.
- Perk reduction read from the payload, reported as a single figure.
- Prerequisite problems surfaced in the panel, with the finish date **withheld**
  whenever the queue cannot be followed.
- Stale queue entries — completed, in progress, or removed from the game —
  dropped and reported rather than silently counted.
- Plan persistence in Tampermonkey storage; collapsible panel.
- 116 tests, zero dependencies.

## Design-vs-code divergences

These are the highest priority because the design document currently describes
behaviour the code does not have. A reader trusting it will be wrong.

### D1 — Only one of three acquisition paths exists

The design specifies an acquisition order: the `educationInitData` fetch, then
React fiber props as a fallback if the endpoint changes shape or name, then a
bundled catalogue snapshot for offline use and preset course lists.

**Only the fetch is implemented.** If Torn renames or reshapes that endpoint,
the tool stops working entirely with no degraded mode. The first probe of this
project confirmed the `sections` array is reachable through the React fiber, so
path 2 is known to be feasible.

Decide before building: is a fallback worth the fragility of reaching into
React internals, or should the design be amended to admit the script depends on
one endpoint? Either answer is defensible; the current state — claiming three
paths and having one — is not.

### D2 — The design claims SPA navigation handling that does not exist

The design states the script "observes for navigation and mounts and unmounts
accordingly rather than assuming one load". There is no `MutationObserver`, no
`popstate` handling, no history patching. The script relies entirely on
`@run-at document-idle`.

Practical effect: navigating to the education page from elsewhere in Torn
without a full reload leaves the panel absent until the player reloads.

Acceptance: navigate from another Torn page to education via the sidebar, with
no reload, and the panel appears. Navigate away and it unmounts cleanly.

### D3 — No catalogue drift notice

The design describes a bundled baseline reconciled against live data, surfacing
a visible notice when they disagree. With no bundled snapshot (see D1) there is
nothing to reconcile against, so this cannot exist as specified. Resolve
alongside D1 — it is the same decision.

## v0.2.0 candidate scope

### 1. Row markers on Torn's own course list

From the design: queued courses receive an ordinal marker and a highlight class
on Torn's list. No text injected into host rows — a class and a marker only,
which is a fraction of the selector dependency inline text would need.

**Unresolved before building:** the 131 `courseWrapper___` elements found during
probing belong to a *progress bar*, not the course rows. The clickable rows
appeared as `goToCourseBtn___`. The real mapping from course id to row element
is not yet known and needs a console probe against the live page.

Every selector must match the stable prefix (`[class*="courseWrapper___"]`),
never a full hashed name — Torn regenerates those hashes on every frontend
rebuild.

### 2. Test the `init()` error path

`init()` wraps `draw()` in a try/catch that renders a visible error rather than
letting a throw become an unhandled rejection and a blank page. It was added in
the pre-release fix wave and **no test exercises it**. The error-model test
covers the fetch-failure path through `buildPanelModel` instead, which is a
different branch.

Parked at the final review as real but not load-bearing. It is the newest
safety net in the file and the only untested one.

### 3. Fix the purity test's false positives

`tests/purity.test.js` scans the engine section as raw text and fails on
`/\bwindow\b/` and `/\blocation\b/`. Those match the ordinary English words in
comments, not just code. This already cost time during the v0.1.0 build: an
agent wrote "window" in a prose comment explaining a numeric range and the suite
failed.

The guard's bias is correct — it fails loudly at edit time and can never produce
a false pass — so this is a papercut, not a defect. Strip comments before
scanning, or tighten the patterns to property-access forms.

### 4. Panel legibility pass

v0.1.0 shipped the minimum styling needed to be readable after live QA found the
panel rendering as one run-on line with black-on-dark buttons. It has not had a
deliberate design pass. The course picker is a bare `<select>` of ~115 entries
with no search or grouping by degree, which is the most obvious rough edge.

### On the floor date (v0.3.0)

The panel is to report two dates: the planned finish using the consumables the
player says they will spend, and a floor computed from scratch using the most
that could physically be spent. The floor is **not** the planned date minus
leftovers — it answers "if I threw everything at this, how fast could it go?"

The two consumables bound differently, and that asymmetry is the point. Books of
Carols are cooldown-bounded, so a schedule of a given length admits only so
many and the ceiling is derived. Job points are not — a player may arrive with a
stockpile banked over months — so the entered figure is used directly.

### On ordering modes (v0.4.0)

Worth restating because it is easy to get wrong: **ordering does not change the
finish date.** Courses run one at a time, so the total is a sum, and a sum is
order-independent. Ordering changes *time-to-benefit* — how early each perk
starts paying off. Several of the community guides in `docs/initial-spec.md`
blur these together. The UI must not.

## Open questions blocking v0.3.0

Moved here from the design document's Open Items. All four need answers from the
game or a live probe, not from the community guides.

1. **Book of Carols reduction.** Sources conflict: "past 2 hours" in one guide,
   "−6 hours" in three others. Absent from the payload. Verify in-game.
2. **Booster cooldown source.** Needed to derive the Book ceiling. Check
   `page.php?sid=UserApiData` and `sidebarAjaxAction.php?q=getBars`; fall back to
   a manual field if neither carries it.
3. **Whether the booster cooldown blocks or stacks.** The ceiling formula
   assumes one Book per cooldown period. Verify alongside item 1.
4. **Whether `actualDuration` updates live** as job points are spent on the
   current course, or only recalculates at course start. Determines whether the
   consumable model can be validated against the payload at all.

## Known and accepted

Not bugs, recorded so nobody re-litigates them.

- **Two code dialects.** The engine uses arrow functions and spread; the runtime
  uses `function () {}` expressions. Cosmetic, judged not worth the churn.
- **Queue removal does not cascade.** Removing a course another depends on
  leaves the queue unfollowable; the honesty backstop withholds the date and
  names what is missing. The player asked for that removal, so it is honoured.
- **The `rfcv` token is read from the `rfc_v` cookie**, falling back to `rfc_id`.
  Confirmed empirically on a live session. If Torn changes this, the panel says
  "could not read your Torn session token" rather than firing a doomed request.

## Lessons that should shape v0.2.0's plan

From the v0.1.0 retrospective, because they were expensive.

- **Fixture-based tests cannot see the HTTP contract.** The `rfcv` requirement
  survived 105 passing tests because the fixture was captured through an
  already-authenticated request. Any v0.2.0 work touching the network needs a
  live check, not just a fixture.
- **Nothing in the automated loop looks at the page.** v0.1.0 shipped through a
  clean final review with no CSS whatsoever. Browser QA is a required gate, not
  a formality.
- **Verify plan values against the fixture before dispatching.** Several v0.1.0
  task briefs carried hand-computed timestamps and course ids that were wrong.
  A one-line script checking them beforehand caught more defects than any review
  stage.
