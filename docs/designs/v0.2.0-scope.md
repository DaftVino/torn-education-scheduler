# Roadmap: v0.2.0 and remaining work

Date: 2026-08-04
Status: scope, not yet a plan. Nothing here has been brainstormed or planned.

This is the single home for every piece of work not shipped in v0.1.0. It exists
because the v0.1.0 execution ledger — which tracked deferred and parked findings
during the build — was deleted when that work merged, and several items lived
only there. Anything not written down here is lost.

Precedence: where this document and
`docs/superpowers/specs/2026-08-03-torn-education-scheduler-design.md` disagree,
**this document is current**. The design doc describes the intended system; the
divergences below record where the shipped code does not match it yet.

## How this is grouped

Releases are grouped by **what each item needs from the project owner**, not by
theme. That is the constraint that actually governs sequencing.

| Release | Gate |
| --- | --- |
| **v0.2.0** | Nothing. Every item can go spec → plan → implement autonomously. Ends at a browser QA gate, as v0.1.0 did. |
| **v0.3.0** | A live console probe, or a decision only the owner can make. |
| **v1.0.0** | The owner's judgement and voice — editorial and design work. |

An item sits in the earliest group whose gate it clears.

## What v0.1.0 shipped

- Reads `page.php?sid=educationInitData` with the `rfcv` anti-CSRF token.
- Adding a course queues its full prerequisite chain, dependency-ordered.
- Exact finish date and time, plus a projected finish per queued course.
- Perk reduction read from the payload, reported as a single figure.
- Prerequisite problems surfaced, with the finish date **withheld** whenever the
  queue cannot be followed.
- Stale queue entries — completed, in progress, or removed from the game —
  dropped and reported rather than silently counted.
- Plan persistence in Tampermonkey storage; collapsible panel.
- 116 tests, zero dependencies.

## v0.2.0 — autonomous build

Everything here is fully specified and needs nothing further from the owner
before implementation. It is a large release; the workstreams below are ordered
by dependency, and cutting it into staged tags at the workstream boundaries is
reasonable if it proves too big to review in one pass.

The release ends at a **browser QA gate**. v0.1.0 proved that gate is not
optional: it passed a clean automated review with no CSS whatsoever, and live QA
then found both a request Torn rejects outright and a finish date missing
two-thirds of the work.

### A. Resilience — do this first

Both items close a gap between what the design promises and what the code does,
and both make everything after them safer to build on.

#### A1 — React fiber fallback for data acquisition

The design specifies three acquisition paths: the `educationInitData` fetch,
then React fiber props if the endpoint changes shape or name, then a bundled
snapshot. **Only the fetch exists.** If Torn renames or reshapes that endpoint,
the tool stops working entirely with no degraded mode.

Path 2 is known feasible — the first probe of this project reached the same
`sections` array through the fiber. Build it as a fallback the fetch-failure path
falls through to, not as a parallel source of truth.

Path 3, the bundled snapshot, is **not** in this release: it carries a staleness
question the owner should answer. See v0.3.0 § H2.

#### A2 — SPA navigation

The design says the script "observes for navigation and mounts and unmounts
accordingly". There is no `MutationObserver`, no `popstate` handling, no history
patching; it relies entirely on `@run-at document-idle`. Navigating to education
from elsewhere in Torn without a reload leaves the panel absent.

Acceptance: navigate from another Torn page via the sidebar with no reload and
the panel appears; navigate away and it unmounts cleanly.

### B. Settings

#### B1 — Settings menu behind a gear icon

A gear icon toggles the panel between the schedule view and a settings view.

**Every variable the arithmetic depends on gets a field here.** No hidden
constants — inferred values, defaults, and anything a later workstream adds. The
shell should absorb new fields without restructuring: a labelled section per
group rather than a flat list.

Fields, across this release:

- Max booster cooldown (hours) — drives the Book ceiling, § D2
- Books of Carols owned or expected — § D2
- Book of Carols unit price — defaults to **13,500,000**, editable, § D2
- Job points available — § D2
- Perk overrides: merits %, Principal rank, WSU stock block — § B2
- Display preferences as they accumulate

#### B2 — Perk inference, and its limits

The panel already reads the total reduction exactly as
`actualDuration / originDuration`. Whether it can infer *which* perks produce
that total is a bounded question with a computed answer.

The three documented perks are merits (0–20% in 2% steps), Principal rank (0 or
10%) and the WSU stock block (0 or 10%), stacking additively:

| Observed total | Decomposition |
| --- | --- |
| 0, 2, 4, 6, 8% | **Unique** — merits only; neither 10% perk fits |
| 10–30% | **Ambiguous — 3 or 4 combinations give the same total** |
| 32, 34, 36, 38, 40% | **Unique** — both 10% perks are forced |

A player showing 20% could hold merits alone, merits with Principal, merits with
the WSU block, or neither 10% perk with full merits. Most players sit in that
ambiguous middle.

**Rule: prefill only where the decomposition is provably unique, mark it as
inferred rather than known, and let the player correct any of it.** Never present
a guess as a reading.

**On consumables corrupting the reading.** In the 2026-08-03 capture the ratio
was exactly `0.6` across all 131 courses including the one in progress, and 0.6
is exactly 20 + 10 + 10. Consumables reduce remaining time on the current course
— `activeCourse.completedAt` — not a course's nominal duration; had they touched
`actualDuration`, the ratio would have varied by course. That is one account at
one moment, so evidence rather than proof. The existing guard already covers the
failure: `parsePayload` reports a non-constant ratio rather than picking a value,
and the panel renders "varies by course". **Keep that guard when adding the
inference.**

### C. Views

#### C1 — Bachelor courses marked in the dropdown

Tier-3 courses unlock things and gate on an entire degree, so they need to stand
out among ~115 entries.

Constraint: styling individual `<option>` elements is unreliable across
browsers. A text marker in the label is the portable answer, and `tier` is
already on every course object. If the picker later becomes a custom listbox,
revisit.

#### C2 — "All courses" option at the top of the dropdown

Picking it **queues every course not yet completed**, dependency-ordered, so the
panel shows the true finish-everything date — the question the community guides
and the old PHP tool both centred on. The queue becomes ~115 rows, which is what
makes § C3 worth building alongside it.

#### C3 — Degree grid view

A second toggle switches to a box grid: one box per degree plus one for all
courses.

**Each box is independent and starts from today** — "if I did only this degree,
starting now, how long?" — including prerequisites it needs and skipping what is
already complete. The twelve boxes therefore do **not** sum to the all-courses
figure, because degrees share prerequisite courses. **Say so in the UI**; a
reader who adds them up and gets a different number will assume the tool is
broken.

### D. Consumables and the floor date

All four mechanics questions that previously blocked this work are resolved.

#### D1 — Resolved mechanics

**Book of Carols: −6 hours of course time, +6 hours of booster cooldown.**
Settles the conflict in the source guides, one of which claimed −2h.

**Booster cooldown is a player-entered maximum, not read from Torn.** No endpoint
probing needed. A booster may be used whenever accumulated cooldown is *below*
the maximum, and the use is allowed even if it pushes the total above it — the
check is on the state before the use, not after.

**Job points update the current course's remaining time in real time.** Torn
applies the reduction immediately, so `activeCourse.completedAt` already reflects
every point spent. Nothing to detect and nothing to correct for, since the script
never knows when a course started.

#### D2 — The ceiling, the floor date, and the price

Cooldown decays in real time, so across a long schedule the ceiling is set by
total cooldown budget rather than by a single sitting:

```text
cooldown budget over a path of length T = T + maxCooldown
maxBooks = floor((T + maxCooldown) / 6h)
```

Each Book also shortens T by 6h, so this is a fixed point with a closed form:

```text
books = (baseTime + maxCooldown) / 12h
```

Worked example on the real 197-day path with a 24h maximum: **396 Books, halving
it to about 98 days.**

**The floor date ships with its cost printed beside it.** At the default
13,500,000 per Book that is about **5.35 billion** — honest arithmetic, but not a
plan anyone executes, and the date alone would mislead. "98 days for 5.35b" is
actionable; "98 days" is not.

The panel reports two dates: the planned finish using what the player says they
will spend, and the floor computed from maximum possible use. The floor is **not**
the planned date minus leftovers.

Job points have no derived ceiling and no cost line — they are earned by working,
not bought, so the entered stockpile is used directly.

### E. Ordering modes

As-listed, shortest-first, days-per-bonus, unlocks-first. All four are
topological sorts over the `parentId` graph with different tiebreaks.

Worth restating because it is easy to get backwards: **ordering does not change
the finish date.** Courses run one at a time, so the total is a sum, and a sum is
order-independent. Ordering changes *time-to-benefit* — how early each perk
starts paying off. Several community guides blur these together. The UI must not.

### F. Export and import

The plan-sharing string from the design: a copyable blob encoding the queue and
modifiers, parsed defensively on import — validated against the catalogue,
unknown ids rejected with a named reason, never evaluated as code. Untrusted
input, treated as such.

### G. Engineering debt

#### G1 — Test the `init()` error path

`init()` wraps `draw()` in a try/catch that renders a visible error rather than
letting a throw become an unhandled rejection and a blank page. Added in the
v0.1.0 pre-release fix wave; **no test exercises it.** The error-model test covers
the fetch-failure path through `buildPanelModel`, a different branch. It is the
newest safety net in the file and the only untested one.

#### G2 — Fix the purity test's false positives

`tests/purity.test.js` scans the engine section as raw text and fails on
`/\bwindow\b/` and `/\blocation\b/`, which match those ordinary English words in
comments. This already cost time during the v0.1.0 build. The guard's bias is
right — it fails loudly at edit time and can never produce a false pass — so this
is a papercut. Strip comments before scanning, or tighten to property-access
forms.

## v0.3.0 — gated on a probe or a decision

Neither item can start until the owner supplies something the script cannot
obtain for itself.

### H1 — Row markers on Torn's course list

**Needs: a live console probe.**

From the design: queued courses receive an ordinal marker and a highlight class
on Torn's own list. No text injected into host rows — a class and a marker only.

The blocker is real. The 131 `courseWrapper___` elements found during probing
belong to a *progress bar*, not the course rows; the clickable rows appeared as
`goToCourseBtn___`. **The course-id-to-row-element mapping is unknown**, and it
cannot be derived from the payload or from the saved page, because React renders
the list client-side. One console probe against the live page settles it.

Every selector must match the stable prefix (`[class*="courseWrapper___"]`),
never a full hashed name — Torn regenerates those hashes on every rebuild.

### H2 — Bundled catalogue snapshot and drift notice

**Needs: a decision on staleness policy.**

The design's third acquisition path is a bundled snapshot, serving as an offline
fallback and as the source for preset course lists. It also underpins the drift
notice — a visible warning when bundled and live data disagree.

The question only the owner can answer: **a committed snapshot goes stale, and a
stale catalogue is exactly the failure this project has already been bitten by.**
The community guides were confidently wrong because nobody re-checked them. Is an
offline fallback worth shipping a second source of truth that can rot?

**A finding that may settle it.** A shared snapshot can only carry fields that
are the same for every player. Checked against the payload on 2026-08-04:
`status` and `actualDuration` both vary by account — the first says what *you*
have completed, the second carries *your* perk reduction. Neither can be
bundled.

So a bundled catalogue would hold `id`, `prefix`, `name`, `description`, `tier`,
`parentId`, `originDuration`, `originCost`, `learningOutcomes` and
`workingStatsGain` — about 55KB, of which 45KB is descriptions and outcomes.
Useful for rendering a course list. **It cannot produce a finish date**, because
it knows neither what you have completed nor how fast you complete things. That
is the one thing this tool exists to do.

The second stated purpose, preset course lists, needs no snapshot either — a
preset is an array of course codes, a few hundred bytes.

**Options:**

1. **Drop path 3.** The React fiber fallback (§ A1) already removes the single
   point of failure, and an offline mode that cannot schedule is not worth 55KB
   plus a staleness problem. Amend the design to say the script depends on the
   live payload, with one in-page fallback.
2. **Ship only the drift notice**, comparing live data against a small bundled
   set of course codes and base durations — enough to detect that Torn changed
   something, without pretending to offline capability.
3. **Ship the full snapshot with a refresh discipline** (below), accepting that
   it degrades to a browsable catalogue rather than a working planner.

**What a refresh discipline would consist of**, if option 3 is chosen:

- The snapshot carries its own capture date, embedded rather than inferred from
  git history.
- Regenerating it is a release-checklist step tied to the `@version` bump, so it
  cannot drift silently between releases.
- A test asserts the snapshot's course set matches the committed fixture,
  catching a forgotten regeneration when the fixture is updated.
- A staleness check fails the suite once the embedded date passes some age. CI
  cannot verify correctness — it cannot authenticate to Torn — so this is a
  reminder, not a guarantee.
- Runtime drift detection compares live against bundled on every successful
  fetch, so every user's browser is a staleness detector and no telemetry is
  needed.
- The fallback path labels its output — "using bundled data captured
  2026-08-03" — so a player reading stale numbers knows they are stale.

## v1.0.0 — gated on the owner's judgement

Editorial and design work. Each needs the owner's eye or voice, and each lands
better once the feature set has stopped moving.

### J1 — Guide presets

**Needs: the starter-path research from § J3.**

Presets fill the queue from a named route. They carry only *which courses* a
route contains, never the guides' claims about what those courses do — the live
payload contradicted the majority of those claims.

Deliberately sequenced after the forum post: **the starter paths written for the
post are the presets.** Doing the research once and shipping it in both places is
the point; building presets first would mean inventing routes twice.

### J2 — Usability design pass

**Needs: the owner's eye.**

A deliberate pass over the whole UI for clarity and usability. v0.1.0 shipped the
minimum styling needed to be legible after live QA found the panel rendering as
one run-on line with black-on-dark buttons; it has had no design attention since,
and v0.2.0 adds a settings view, a grid view and several new controls on top.

Stated priority: **usability over presentation.** Clean and clear beats
attractive.

### J3 — Forum post

**Needs: the owner's voice, and a fresh payload capture.**

A guide to education for a complete beginner, for the Torn forums.

- Aimed at a total novice — what education is, why starting early matters, how
  tiers and prerequisites work.
- **Better organised and more engaging than the nine guides** in
  `docs/initial-spec.md`. Those are long, repetitive, and contradict each other.
- Ends with a short advertisement for the script and where to download it. The
  Greasy Fork link comes later; leave a clear placeholder.

#### The payload is the source of truth

**Every factual claim is checked against `educationInitData` and nothing else** —
not the nine guides, not this repository's prose, not recollection. It is Torn's
own backend response, the data the page renders *from*, with no transcription
layer in between.

Not a formality: the guides are wrong often enough that writing from them would
reproduce their errors under a new byline, and a post whose selling point is "the
old guides are wrong" is exactly what readers will fact-check.

**Re-capture before publishing.** `tests/fixtures/education-init-data.json` is a
2026-08-03 snapshot of one account. Fetch a fresh payload, diff it against the
fixture, and confirm every claim still holds. Regenerate with
`node scripts/scrub-fixture.mjs` after dropping a fresh capture into
`tests/fixtures/raw/`.

#### Starter paths — 3 to 6 of them

Concrete opening paths, one per gameplay type, so a reader leaves with something
to enrol in rather than a wall of options.

- **3 to 6 paths**, each aimed at a recognisable player type — fighting, crime,
  money, undecided. Pick archetypes from what the courses actually reward.
- **Assume a poor new player**: no Book of Carols, no job points, no merits, no
  Principal rank, no stock block. Time and almost nothing else.
- **First 6 to 12 months only.** Opening paths, not routes to finishing
  education. Say where each ends and why that is a sensible place to reassess.
- **Balance them mathematically.** Rank candidates by benefit per day and justify
  the order — each path should survive "why not this course instead?".
- Give each a total in days and dollars, and a 6-month checkpoint.

Two methodological traps, both confirmed in a trial run on 2026-08-04:

1. **Use `originDuration`, never `actualDuration`.** The fixture's
   `actualDuration` carries the capturing account's 40% reduction. A new player
   has none of it, so every published figure must come from `originDuration`, or
   the paths will promise roughly a third less time than they take. The single
   easiest way to get this section wrong.
2. **Validate every path with `validateQueue` against an empty completed set.**
   Prerequisite chains are not obvious by eye — several Computer Science courses
   hang off `CMT2530` rather than the intro, so a hand-written crime path can
   look right and be unfollowable.

A trial run of five candidate archetypes came out between 84 and 336 days and
$2,400 to $28,530, all prerequisite-clean, so the shape is workable. The paths
are not written and are not fixed by that run.

#### Which degrees not to start early

Business runs 259 days and pays off only for a company director; Law is 266 days
for busting and bailing, which the guides themselves call inefficient. Naming
what to skip is as useful to a new player as naming what to take, and no existing
guide leads with it.

#### Verified corrections as material

Confirmed against the payload on 2026-08-04. Useful for a "what the old guides
get wrong" section, which doubles as the credibility hook — each is checkable by
any reader in about ten seconds.

| Course | Guides claim | Game returns |
| --- | --- | --- |
| BIO2410 Anatomy | +5% crit (five guides) | **3% chance increase of achieving a critical hit** |
| MTH3330 Bachelor of Mathematics | +30% ammo | **20% bonus to ammo conservation** |
| CBT2820 Study of Machine Guns | +5% accuracy | **+1.00 accuracy increase** — flat, not a percentage |
| DEF2730 Krav Maga | +1% defense | **2% passive bonus to defense** |
| BIO2380 Neurobiology | damage to the *neck* | damage to an opponent's **throat** |
| BIO2400 Forensic Science | stealth −25% | **decrease stealthiness by 0.5** |
| HAF3111 | 50% decrease in escape chance | **25% increase in speed during an escape attempt** |
| DEF3770 | "Master of Self Defense" | **"Bachelor of Self Defense"** |
| LAW2910 | "Law of Property" | **"Property Law"** |
| BIO1340 | "Introduction to Biology" | **"Introduction to Biochemistry"** |

The pattern is the story: on the first three rows the *majority* of guides agree
with each other and are wrong, while a lone dissenter had Anatomy and the
Mathematics bachelor right. Consensus among stale sources is not evidence.

The strongest correction is not in the table. Guide 7 states outright that
education reductions multiply — "the max you can get from perks is
.8\*.9\*.9 = .648". They add. An account holding all three documented perks shows
exactly 0.60, which is 20 + 10 + 10, and a larger reduction than the guides say
is possible. Re-confirm against a fresh payload before asserting it: it rests on
one account's perk set.

The payload also contains courses no guide mentions — `CMT2230`, `CMT2130`,
`CMT2131`, `CMT2128`, `CMT2129`, `PSY2132`, `CMT2570`, `CMT2590`, `GEN2114` —
added for Crimes 2.0, years after most of those posts. The cleanest illustration
of why a maintained tool beats a forum post from 2019.

## Known and accepted

Not bugs. Recorded so nobody re-litigates them.

- **Two code dialects.** The engine uses arrow functions and spread; the runtime
  uses `function () {}` expressions. Judged not worth the churn.
- **Queue removal does not cascade.** Removing a course another depends on leaves
  the queue unfollowable; the honesty backstop withholds the date and names what
  is missing. The player asked for that removal, so it is honoured.
- **The `rfcv` token is read from the `rfc_v` cookie**, falling back to `rfc_id`.
  Confirmed empirically. If Torn changes this, the panel says "could not read
  your Torn session token" rather than firing a doomed request.

## Lessons that should shape the next plan

From the v0.1.0 build, because they were expensive.

- **Fixture-based tests cannot see the HTTP contract.** The `rfcv` requirement
  survived 105 passing tests because the fixture was captured through an
  already-authenticated request. Any work touching the network needs a live
  check, not just a fixture.
- **Nothing in the automated loop looks at the page.** v0.1.0 passed a clean
  final review with no CSS whatsoever. Browser QA is a required gate.
- **Verify plan values against the fixture before dispatching.** Several v0.1.0
  task briefs carried hand-computed timestamps and course ids that were wrong. A
  one-line script checking them beforehand caught more defects than any single
  review stage.
