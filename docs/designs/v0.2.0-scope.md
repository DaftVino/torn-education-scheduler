# Roadmap: v0.2.0 and remaining work

Date: 2026-08-04
Status: scope, not yet a plan. Nothing here has been brainstormed or planned.

This is the single home for every piece of work not shipped in v0.1.0. It exists
because the v0.1.0 execution ledger — which tracked deferred and parked findings
during the build — was deleted when that work merged, and several items lived
only there. Anything not written down here is lost.

Precedence: where this document and
`docs/superpowers/specs/2026-08-03-torn-education-scheduler-design.md` disagree,
**this document is current**. The design doc describes the intended system; the
divergences below record where the shipped code does not match it yet.

## What v0.1.0 actually shipped

Recorded because the design's release table claimed some of this for v0.2.0.

- Reads `page.php?sid=educationInitData` with the `rfcv` anti-CSRF token.
- Adding a course queues its full prerequisite chain, dependency-ordered.
- Exact finish date and time, plus a projected finish per queued course.
- Perk reduction read from the payload, reported as a single figure.
- Prerequisite problems surfaced in the panel, with the finish date **withheld**
  whenever the queue cannot be followed.
- Stale queue entries — completed, in progress, or removed from the game —
  dropped and reported rather than silently counted.
- Plan persistence in Tampermonkey storage; collapsible panel.
- 116 tests, zero dependencies.

## Design-vs-code divergences

Highest priority: the design document currently describes behaviour the code
does not have, so a reader trusting it will be wrong.

### D1 — Only one of three acquisition paths exists

The design specifies an acquisition order: the `educationInitData` fetch, then
React fiber props as a fallback if the endpoint changes shape or name, then a
bundled catalogue snapshot for offline use and preset course lists.

**Only the fetch is implemented.** If Torn renames or reshapes that endpoint,
the tool stops working entirely with no degraded mode. The first probe of this
project confirmed the `sections` array is reachable through the React fiber, so
path 2 is known to be feasible.

Decide before building: is a fallback worth the fragility of reaching into React
internals, or should the design be amended to admit the script depends on one
endpoint? Either answer is defensible; claiming three paths and having one is
not.

### D2 — The design claims SPA navigation handling that does not exist

The design says the script "observes for navigation and mounts and unmounts
accordingly". There is no `MutationObserver`, no `popstate` handling, no history
patching. It relies entirely on `@run-at document-idle`.

Effect: navigating to the education page from elsewhere in Torn without a full
reload leaves the panel absent until the player reloads.

Acceptance: navigate from another Torn page via the sidebar with no reload and
the panel appears; navigate away and it unmounts cleanly.

### D3 — No catalogue drift notice

The design describes a bundled baseline reconciled against live data with a
visible notice when they disagree. With no bundled snapshot (see D1) there is
nothing to reconcile against. Same decision as D1.

## v0.2.0 scope

### 1. Settings menu behind a gear icon

A gear icon toggles the panel between the schedule view and a settings view
holding everything the player might need to set. Confirmed requirement.

Settings to house, current and anticipated:

- **Max booster cooldown** (hours) — drives the Book of Carols ceiling in
  v0.3.0. See item 7.
- **Books of Carols owned / expected** — see item 7.
- **Book of Carols unit price** — defaults to **13,500,000**, the current market
  average. Editable, because item-market prices drift and a hardcoded figure
  would quietly go stale. Feeds the cost line beside the floor date (item 8).
- **Job points available** — see item 7.
- What-if perk overrides — the design sanctions these; not built. Additive
  stacking is confirmed, so a subset override is computable.
- Panel display preferences as they accumulate.

The shell should carry settings it does not yet have fields for without
restructuring — a labelled section per group rather than a flat list.

**Every variable the script uses gets a field here.** Nothing stays a hidden
constant. That includes values inferred from the payload, values with sensible
defaults, and anything a future release adds — if the arithmetic depends on it,
the player can see it and change it.

#### Inferring perks from the observed reduction

The panel already reads the total reduction exactly, as
`actualDuration / originDuration` across every course. The question is whether
it can also infer *which* perks produce that total, to prefill the settings.

**The total is always exact. The breakdown usually is not.** The three documented
perks are merits (0–20% in 2% steps), Principal rank (0 or 10%) and the WSU
stock block (0 or 10%), stacking additively. Enumerating every combination:

| Observed total | Decomposition |
| --- | --- |
| 0, 2, 4, 6, 8% | **Unique** — merits only; neither 10% perk can fit |
| 10–30% | **Ambiguous — 3 or 4 combinations give the same total** |
| 32, 34, 36, 38, 40% | **Unique** — both 10% perks are forced |

A player showing 20% could hold merits alone, merits with Principal, merits with
the WSU block, or neither 10% perk with full merits. Four different answers, one
number. Most players will sit in that ambiguous middle band.

So the rule is: **prefill only where the decomposition is provably unique, mark
it as inferred rather than known, and let the player correct any of it.** Never
present a guess as a reading. In the ambiguous band, show the total and leave the
individual perk fields for the player to set.

#### On whether consumables corrupt the reading

The concern is fair: if a Book of Carols or job points altered `actualDuration`,
the inferred total would be wrong.

Current evidence says they do not. In the 2026-08-03 capture the ratio was
exactly `0.6` across all 131 courses, including the one in progress, and 0.6 is
exactly 20 + 10 + 10. Consumables reduce the *remaining time on the current
course* — which is `activeCourse.completedAt` — not a course's nominal duration.
Had they touched `actualDuration`, the ratio would have varied by course rather
than holding to a single value.

That is one account at one moment, so it is evidence rather than proof. The
existing guard already covers the failure: `parsePayload` reports the ratio as
non-constant instead of picking a value, and `reductionLabel` renders "varies by
course". If consumables ever do perturb it, the panel says so rather than
inferring from a number it should not trust. Keep that guard when adding the
inference.

### 2. Highlight bachelor courses in the dropdown

Tier-3 courses are the ones that unlock things and gate on an entire degree, so
they need to stand out among ~115 entries.

Note a real constraint: styling individual `<option>` elements is unreliable
across browsers. A text marker in the option label is the portable answer — the
tier is already on every course object, so this is display-only. If the picker
later becomes a custom listbox rather than a native `<select>`, revisit.

### 3. "All courses" option at the top of the dropdown

Picking it **queues every course not yet completed**, dependency-ordered, so the
panel shows the true finish-everything date. That is the question the community
guides and the old PHP tool both centred on.

The queue becomes roughly 115 rows, which is what makes the grid view (item 4)
worth building alongside it.

### 4. Degree grid view

A second toggle switches the display to a clean box grid: one box per degree
plus one for all courses.

**Each box is independent and starts from today** — "if I did only this degree,
starting now, how long?" — including prerequisites it needs and skipping what is
already complete. The twelve boxes therefore do **not** sum to the all-courses
figure, because degrees share prerequisite courses. Say so in the UI; a reader
who adds them up and gets a different number will assume the tool is broken.

Presentation is a grid of name plus time. Keep it compact enough to scan.

### 5. Row markers on Torn's own course list

From the design: queued courses receive an ordinal marker and a highlight class
on Torn's list. No text injected into host rows — a class and a marker only.

**Unresolved before building:** the 131 `courseWrapper___` elements found during
probing belong to a *progress bar*, not the course rows. The clickable rows
appeared as `goToCourseBtn___`. The course-id-to-row-element mapping is not yet
known and needs a console probe against the live page.

Every selector must match the stable prefix (`[class*="courseWrapper___"]`),
never a full hashed name — Torn regenerates those hashes on every rebuild.

### 6. Carried-over engineering items

- **Test the `init()` error path.** `init()` wraps `draw()` in a try/catch that
  renders a visible error rather than letting a throw become an unhandled
  rejection and a blank page. It was added in the pre-release fix wave and no
  test exercises it — it is the newest safety net in the file and the only
  untested one.
- **Fix the purity test's false positives.** `tests/purity.test.js` scans the
  engine section as raw text and fails on `/\bwindow\b/` and `/\blocation\b/`,
  which match those ordinary English words in comments. This already cost time
  during the v0.1.0 build. The guard's bias is right — it fails loudly at edit
  time and can never produce a false pass — so this is a papercut. Strip
  comments before scanning, or tighten to property-access forms.

## v0.3.0 — consumables and the floor date

### 7. Resolved mechanics

Answered by the project owner on 2026-08-04. These settle three of the four
questions that previously blocked this release.

**Book of Carols: −6 hours of course time, +6 hours of booster cooldown.** This
resolves the conflict in the source guides, where one claimed −2h. The value is
now a known constant, not a disputed one.

**Booster cooldown is a player-entered maximum, not a value read from Torn.** No
endpoint probing needed. A booster may be used whenever accumulated cooldown is
*below* the maximum, and the use is allowed even if it pushes the total above
that maximum — the check is on the state before the use, not after.

**Job points update the current course's remaining time in real time.** Torn
applies the reduction immediately, so `activeCourse.completedAt` already
reflects every job point already spent. There is nothing to detect and nothing
to correct for, because the script never knows when a course started. This
closes the old open item about whether `actualDuration` updates live.

### 8. The Book ceiling, and what it comes to

Cooldown decays in real time, so across a long schedule the ceiling is set by
total cooldown budget rather than by a single sitting:

```text
cooldown budget over a path of length T = T + maxCooldown
maxBooks = floor((T + maxCooldown) / 6h)
```

Each Book also shortens T by 6h, so this is a fixed point. It resolves in closed
form:

```text
books = (baseTime + maxCooldown) / 12h
```

Worked example on the real 197-day path with a 24h maximum: **396 Books, which
halves the path to about 98 days.**

**That figure gets its price printed beside it.** Agreed 2026-08-04: the panel
shows what the floor date would cost in Books, not just the date.

At the default 13,500,000 per Book, 396 of them is about **5.35 billion** — so
the floor is honest arithmetic but not a plan anyone will execute, and the date
alone would mislead. The cost line is what makes it useful: it turns "you could
finish in 98 days" into "you could finish in 98 days for 5.35b", which a player
can actually act on.

The unit price is a setting (see item 1) rather than a constant, defaulting to
13,500,000. Item-market prices drift, and a hardcoded number would go stale
without anyone noticing — the same failure this project already hit with the
community guides' duration figures.

Job points have no equivalent cost line: they are earned by working, not bought,
so the honest ceiling there is the stockpile the player types in.

### 9. Two dates

The panel reports the planned finish, using the consumables the player says they
will spend, and the earliest-possible finish, computed from scratch using the
most that could physically be spent. The floor is **not** the planned date minus
leftovers — it answers "if I threw everything at this, how fast could it go?"

Job points remain unbounded by the schedule: a player may arrive with a
stockpile banked over months, so the entered figure is used directly with no
derived ceiling.

## v0.4.0 — ordering modes

As-listed, shortest-first, days-per-bonus, unlocks-first.

Worth restating because it is easy to get backwards: **ordering does not change
the finish date.** Courses run one at a time, so the total is a sum, and a sum is
order-independent. Ordering changes *time-to-benefit* — how early each perk
starts paying off. Several community guides in `docs/initial-spec.md` blur these
together. The UI must not.

## v0.5.0 — presets and sharing

Guide presets drawn from the community posts, and the export/import plan string.
Presets carry only *which courses* a route contains, never the guides' claims
about what those courses do — the live payload contradicted the majority of
those claims.

## v1.0.0 — polish and launch

### 10. Usability design pass

A deliberate pass over the whole UI for clarity and usability. v0.1.0 shipped the
minimum styling needed to be legible after live QA found the panel rendering as
one run-on line with black-on-dark buttons; it has had no design attention since.

Stated priority: **usability over presentation.** Clean and clear beats
attractive.

### 11. Forum post

A guide to education for a complete beginner, to be posted on the Torn forums.
Requirements as given:

- Aimed at a total novice — what education is, why starting early matters, how
  the tiers and prerequisites work.
- **Better organised and more engaging than the nine guides** collected in
  `docs/initial-spec.md`. Those are long, repetitive, and contradict each other.
- Ends with a short advertisement for the script and where to download it.
- The Greasy Fork link will be supplied later; leave a clear placeholder.

#### The `educationInitData` payload is the source of truth

**Every factual claim in the post is checked against the payload, and against
nothing else.** Not the nine community guides in `docs/initial-spec.md`, not
this repository's own prose, not recollection. The payload is Torn's own backend
response, carrying structured `learningOutcomes`, `originDuration`,
`actualDuration`, `tier` and `parentId` for all 131 courses — the data the page
renders *from*, with no transcription or parsing layer between the game and the
text.

This is not a formality. The guides are wrong often enough that writing from
them would reproduce their errors under a new byline, and a post whose selling
point is "the old guides are wrong" is precisely the thing readers will
fact-check. Every correction it asserts must survive someone opening their own
education page.

**Re-capture before publishing.** `tests/fixtures/education-init-data.json` is a
snapshot taken 2026-08-03. If Torn rebalances a course between then and
publication, the fixture will not know. Fetch a fresh payload, diff it against
the fixture, and confirm every claim the post makes still holds. Regenerate with:

```
node scripts/scrub-fixture.mjs
```

after dropping a fresh capture into `tests/fixtures/raw/`.

**Provenance, stated honestly:** the payload reaches this repository through a
logged-in browser session, not from anyone reading the site. That makes it
stronger than "the wiki says" — it is the server's own answer — but it is a
point-in-time capture of one account, and the reduction figures in it reflect
that account's perks rather than a new player's.

#### Starter paths — 3 to 6 of them

The post carries a small set of concrete starting paths, one per gameplay type,
so a new player leaves with something to actually enrol in rather than a wall of
options.

Requirements:

- **3 to 6 paths**, each aimed at a recognisable type of player — fighting,
  crime, money, undecided, and so on. Pick the archetypes from what the courses
  actually reward, not from the guides' framing.
- **Assume a poor new player**: no Book of Carols, no job points, no merits, no
  Principal rank, no stock block. They have time and almost nothing else.
- **Cover roughly the first 6 to 12 months only.** These are opening paths, not
  routes to finishing education. Say where each path ends and why that is a
  sensible place to stop and reassess.
- **Balance them mathematically**, not by reputation. Rank candidate courses by
  benefit per day and justify the order — a path should be defensible against
  "why not this course instead?".
- Give each path a total in days and dollars, and a 6-month checkpoint so a
  reader can see how far they get in half the time.

Two methodological traps, both confirmed by a trial run on 2026-08-04:

1. **Use `originDuration`, never `actualDuration`.** The committed fixture's
   `actualDuration` values carry the capturing account's 40% perk reduction. A
   new player has none of those perks, so every published figure must come from
   `originDuration` or the paths will promise roughly a third less time than
   they take. This is the single easiest way to get the whole section wrong.
2. **Validate every path with `validateQueue` against an empty completed set.**
   Prerequisite chains are not obvious by eye — several Computer Science courses
   hang off `CMT2530` rather than the intro, so a hand-written crime path can
   look right and be unfollowable. The engine already answers this; use it
   rather than reasoning it through.

A trial run of five candidate paths came out between 84 and 336 days and $2,400
and $28,530, all prerequisite-clean, so the shape is workable — but the paths
themselves are not yet written and are not fixed by that run.

Also worth a short section: **which degrees not to start early.** Business runs
259 days and pays off only for a company director; Law is 266 days for busting
and bailing, which the guides themselves call inefficient. Naming what to skip
is as useful to a new player as naming what to take, and no existing guide leads
with it.

#### Verified corrections available as material

Confirmed against the payload on 2026-08-04. Useful for a "what the old guides
get wrong" section, which doubles as the post's credibility hook — each is
checkable by any reader in about ten seconds.

| Course | Guides claim | Game returns |
| --- | --- | --- |
| BIO2410 Anatomy | +5% crit (five guides) | **3% chance increase of achieving a critical hit** |
| MTH3330 Bachelor of Mathematics | +30% ammo | **20% bonus to ammo conservation** |
| CBT2820 Study of Machine Guns | +5% accuracy | **+1.00 accuracy increase** — flat, not a percentage |
| DEF2730 Krav Maga | +1% defense | **2% passive bonus to defense** |
| BIO2380 Neurobiology | damage to the *neck* | damage when hitting an opponent's **throat** |
| BIO2400 Forensic Science | stealth −25% | **decrease stealthiness by 0.5** |
| HAF3111 | 50% decrease in escape chance | **25% increase in speed during an escape attempt** |
| DEF3770 | "Master of Self Defense" | **"Bachelor of Self Defense"** |
| LAW2910 | "Law of Property" | **"Property Law"** |
| BIO1340 | "Introduction to Biology" | **"Introduction to Biochemistry"** |

Note the pattern worth writing about: on the first three rows the *majority* of
guides agree with each other and are wrong. A lone dissenting guide had Anatomy
and the Mathematics bachelor right. Consensus among stale sources is not
evidence.

The strongest single correction is not in that table. Guide 7 states outright
that education time reductions multiply — "the max you can get from perks is
.8*.9*.9 = .648". They add. An account holding all three documented perks shows
exactly 0.60, which is 20 + 10 + 10, and is a larger reduction than the guides
say is even possible. Re-confirm against a fresh payload before asserting it,
since it rests on one account's perk set.

The live data also contains courses no guide mentions at all — `CMT2230`,
`CMT2130`, `CMT2131`, `CMT2128`, `CMT2129`, `PSY2132`, `CMT2570`, `CMT2590`,
`GEN2114` — evidently added for Crimes 2.0, years after most of those posts were
written. That is the cleanest illustration of why a maintained tool beats a
forum post from 2019.

## Known and accepted

Not bugs. Recorded so nobody re-litigates them.

- **Two code dialects.** The engine uses arrow functions and spread; the runtime
  uses `function () {}` expressions. Judged not worth the churn.
- **Queue removal does not cascade.** Removing a course another depends on leaves
  the queue unfollowable; the honesty backstop withholds the date and names what
  is missing. The player asked for that removal, so it is honoured.
- **The `rfcv` token is read from the `rfc_v` cookie**, falling back to `rfc_id`.
  Confirmed empirically. If Torn changes this, the panel says "could not read
  your Torn session token" rather than firing a doomed request.

## Lessons that should shape the next plan

From the v0.1.0 build, because they were expensive.

- **Fixture-based tests cannot see the HTTP contract.** The `rfcv` requirement
  survived 105 passing tests because the fixture was captured through an
  already-authenticated request. Any work touching the network needs a live
  check, not just a fixture.
- **Nothing in the automated loop looks at the page.** v0.1.0 passed a clean
  final review with no CSS whatsoever. Browser QA is a required gate.
- **Verify plan values against the fixture before dispatching.** Several v0.1.0
  task briefs carried hand-computed timestamps and course ids that were wrong. A
  one-line script checking them beforehand caught more defects than any single
  review stage.
