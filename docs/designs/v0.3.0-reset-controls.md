# v0.3.0 § H4 — Reset controls

**Status:** spec, ready to plan.
**Date:** 2026-08-04
**Depends on:** § H3 (focus mode) for the focus view's existence. The schedule
and settings buttons do not depend on it and can ship first.

## What this is

Three buttons, one per view that owns player data:

| View | Button | Clears |
| --- | --- | --- |
| Schedule (home) | `reset` | The course queue |
| Focus | `reset` | Every focus selection |
| Settings | `defaults` | Every field on the settings page |

Each sits **at the right-hand end of the nav row**, on the same line as the
`schedule` / `degrees` / `focus` / `settings` buttons, pushed right so it reads
as a different kind of control than the ones that only change what you are
looking at.

The Degrees view gets no button. It owns nothing — every box is computed from
the catalogue and today's date, so there is nothing there to reset.

## Placement

The nav row already exists at [line 1904](../../torn-education-scheduler.user.js#L1904)
and is already `display: flex`. The reset button is appended after the view
buttons and pushed right with `margin-left: auto`, which is the whole layout
change:

```css
#tes-panel .tes-nav .tes-reset { margin-left: auto; }
```

**Not the header.** `.tes-header` is one click-to-collapse div, so a control
placed there would collapse the panel on its way to doing its job. The nav row
needs no such surgery, and its existing `handlers !== noopHandlers` guard
already answers the "panel that cannot respond" case for free.

The nav row is not rendered while the panel is collapsed, so the button is
absent then. That is correct: there is nothing on screen to reset.

## The rule that makes this predictable

**A button resets what its own page owns, and nothing else.**

This is the whole design. Without it, "reset" on one page silently reaching
into another's data is a bug the player finds by losing work.

The consequence worth stating plainly: **`defaults` on the settings page does
not clear the focus list.** Focuses are stored inside the settings object, so
this is a deliberate exception in the implementation, not a natural consequence
of it — resetting settings must preserve `focuses` verbatim. The focus page has
its own button, and a player who resets their booster cooldown has said nothing
about what they are trying to build toward.

**Collapsed state is never reset by anything.** It is a standing preference,
not data a page owns — the same reasoning that keeps it out of the view state.

## Resetting is destructive, so it asks first

A queue is a plan the player built by hand, one course at a time. Clearing it
is not recoverable — there is no undo in this panel and no history in storage.

This repo has already shipped this exact bug once. From the v0.2.0 handoff log:
*"a stray `add` click before the player touched the picker queued all ~115
courses with no bulk-undo."* A one-click destructive control sitting in the same
row as four harmless navigation buttons is the same mistake with the sign
flipped — and the shared row makes the misclick *more* likely, not less.

So every reset button is **two clicks**:

1. First click **arms** it. The label becomes `reset — sure?` (or
   `defaults — sure?`) and the button takes a warning colour.
2. Second click applies it.

**Disarming** happens on any of: changing view, collapsing the panel, or
clicking anything else in the panel. The armed flag lives in `init()`'s closure
and is **never persisted** — it describes one moment, like `importError`
already does. A panel reopened later is never found still armed.

No timer. A countdown that disarms on its own is a race with the player's
attention, and it cannot be tested without faking clocks.

## The perk-inference wrinkle

`prefillPerks` fills a perk field only where the stored value is `null` — "has
not said". `defaults` sets every perk back to `null`. So **the very next redraw
re-fills the perk fields from inference**, and the player sees numbers reappear
in fields they just cleared.

That behaviour is correct and must not be suppressed: `null` genuinely means
"has not said", inference genuinely applies to unsaid fields, and adding a
session-scoped "no really, leave them blank" flag would create a fourth kind of
empty that nothing persists.

**But it looks broken**, so the settings view must say so in words next to the
button — that the perk fields refill from what the panel inferred, and that
typing over them is what makes a value yours. Without that line, the honest
behaviour reads as a button that does not work.

## Behaviour

| Condition | Behaviour |
| --- | --- |
| Reset applied, storage write succeeds | Panel redraws with the cleared data |
| Reset applied, storage write fails | Existing `saveError` / `settingsSaveError` line renders; the in-memory reset still stands, as with every other write |
| Panel is on the error model (`noopHandlers`) | No nav row renders, so no button — the existing guard, unchanged |
| Panel is collapsed | No nav row, no button |
| Queue is already empty | Button still renders, still arms, applies to nothing. Hiding it would make its absence a puzzle |
| Settings already at defaults | Same |
| Armed, then the view changes | Disarmed, nothing applied |
| Armed, then the panel is collapsed | Disarmed, nothing applied |

## Testing

Additions to `tests/panel.test.js`, plus `tests/settings.test.js` for the
defaults-preserve-focuses rule and `tests/storage.test.js` for the armed flag.

1. Each of the three views renders its button in the nav row; Degrees renders
   none.
2. The button is the **last** child of `.tes-nav`, so `margin-left: auto`
   pushes the right thing.
3. One click arms and changes the label. It does **not** clear anything —
   asserted against the stored plan, not just the rendered panel.
4. Two clicks clear.
5. Changing view disarms; a subsequent single click on the new view's button
   arms rather than applies.
6. Collapsing disarms.
7. `defaults` leaves `settings.focuses` untouched while resetting every other
   field.
8. Schedule `reset` leaves settings untouched; focus `reset` leaves the queue
   untouched.
9. A failed storage write surfaces the existing error line.
10. The armed flag never reaches storage — assert on what `GM_setValue` was
    handed.
11. The settings view carries the inference-refill sentence.

## What this does not change

- `.tes-header`, which keeps its current click-to-collapse behaviour untouched.
- The security surface: no new storage key, no new grant, no network.
- Zero dependencies, no build step.
- Every do-not-revert item in the v0.2.0 handoff log.
- `collapsed`, which no reset touches.
