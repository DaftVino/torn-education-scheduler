# v1.3.0 — Path summary toggle

**Status:** built on `feat/path-summary`; awaiting manual QA
(`docs/qa-checklist.md` § P). The plan was approved in #9, after an own eng
review plus an adversarial Codex review.
**Issue:** #8
**Date:** 2026-10-08
**Plan:** `docs/designs/v1.3.0-path-summary-plan.md`

## What this is

A `summary` button in the nav row, placed directly after `focus` and styled
with an inverted colour scheme. Selecting it opens a compact block at the top
of the Schedule overview, above the `Queue fin:` line. The block answers the
question the panel cannot answer today: *what does this whole path get me?*

The summary is transient. It closes when the player uses any other tab or
control, and it is never written to storage.

## Why it exists

The Schedule view answers *when*, through the finish date and the booster
scenarios. It never answers *what*. A queue's gains are spread across one
indented bonus line per row, and nothing adds them up. A player comparing a
40-course plan with a 60-course plan has to scroll both queues and total them
by hand.

## Decisions

These were open questions in the request. Each is settled here so the plan
has nothing left to guess. The owner can overturn any of them on the PR.

| # | Question | Decision | Why |
| --- | --- | --- | --- |
| D1 | Where does it render? | Inside `.tes-schedule-overview`, as its first child, above `.tes-finish`. | The request names the Queue fin box, and the overview is the box that holds it. Rendering inside the overview keeps one outlined surface rather than stacking two. |
| D2 | What does the button do off the Schedule view? | It switches to Schedule **and** opens the summary in one click. | The Queue fin box exists only on Schedule. A button that does nothing on three of four views would read as broken. |
| D3 | What closes it? | Every handler invocation except the summary's own toggle. This is enforced by **wrapping** the handler set, and the wrapper **redraws** whenever it closed an open summary and the handler itself did not draw. A click that reaches no handler (a disabled control, `add` with the placeholder still selected) changes nothing and leaves it open. | The request says "whenever another tab or option is selected". `resetArmed` is cleared in about 20 handlers by hand, which is how a future handler forgets it. The redraw is needed because some handlers change closure state without drawing: `onPickerChange` returns without a redraw, so without it a closed summary would stay on screen. |
| D4 | Does a second click close it? | Yes. The button is a toggle, with `aria-pressed` reflecting the state. | That is what "toggle button" means. |
| D5 | Is it persisted? | No. It lives in `init()`'s closure beside `resetArmed`. A fresh `init()` (route change, remount) starts closed. | The same rule `view` and `resetArmed` already follow: the panel you last looked at is not a preference. |
| D6 | What when there is no honest finish date? | The button stays visible but is **disabled**, with a reason-specific `title`: no course data, an empty queue, or unmet prerequisites. The loading shell and the fatal error panel render no nav row at all (they use `noopHandlers`), so they carry no button. | `buildPanelModel` withholds `finishLabel` and `totalLabel` whenever the queue cannot be followed. A summary of an unfollowable path would print totals the panel elsewhere refuses to stand behind. Disabled rather than absent, so the nav row does not reflow as the queue changes. One reason string per cause, so a fetch failure is not misdiagnosed as a queue problem. |
| D7 | Which colour scheme is "inverted"? | Closed: light fill (`--tm-text`) with dark text. Open (pressed): green fill (`--tm-good-text`) with the same dark text. | Every other button is light text on a dark fill. This is the only control in the panel that is the reverse, which is the point. |
| D8 | How are improvements totalled? | One figure per `(category, selection)`, never summed across selections or units. Within a category, percent items come first, then flat items, then count items. Units are never ranked against each other. | The same rule focus mode is built on (`docs/designs/v0.3.0-focus-mode.md`). Adding a percent bonus to a flat stat invents an exchange rate, and so does ranking `+12` effectiveness against `+11%` productivity to decide which one is shown. |
| D9 | Does the summary show the Books floor date? | **No.** | The Schedule code holds that a floor date without its Book count and cost is "a number nobody can act on", and the booster block directly below the summary already shows the floor with both. A bare floor date in the summary would reintroduce exactly that. |
| D10 | What happens to a category with more items than fit on a line? | The first four show, then `+N more`. The whole line is a native `<details>` disclosure, so the full list is one tap away. | Codex review: the all-remaining queue has 32 unlocks and 16 combat bonuses. A permanent `+28 more` would hide most of what the summary exists to show. A native disclosure needs no handler, so opening it does not close the summary. |
| D11 | Which data-health warning applies? | Only mismatches **on the queued courses**: taxonomy rows whose outcome text Torn no longer shows, plus outcome strings on queued courses the taxonomy never claimed. | The catalogue-wide `focusHealth` would warn a three-course queue about a course it does not contain. The Focus view keeps the catalogue-wide figure. |

## What the summary shows

Order is fixed. Each line is omitted when it has nothing to say, never shown
empty.

1. **Headline.** `23 courses · 2 degrees · 87 days 4 hrs queued`. The course
   count is the ordered queue's length. Degrees are queued tier-3 courses,
   and that part is dropped at zero. The time is `model.totalLabel`, the same
   figure as `Total queued time`. The word `queued` is load-bearing: the
   finish date also waits for the active course, so an unlabelled duration
   beside it would read as wrong.
2. **Finish.** `Finishes 2027-01-04 · 13:00 TCT`, reusing `model.finishLabel`.
   It repeats `Queue fin:` one line below, but the request asks for the finish
   date in the summary, and the summary should read whole on its own.
3. **Working stats.** `Working stats: +1,240 intelligence · +600 endurance ·
   +300 manual labor`. A stat with a zero total is omitted.
4. **Bonuses.** One line per taxonomy category with a non-zero contribution,
   in `FOCUS_CATEGORIES` order, excluding Working Stats.
   `Category: item · item · item · item · +N more` (see D10).
   - percent items render as `selection +N%`, largest first
   - flat items render as `selection +N`, largest first
   - count items (unlocks, and anything in `FOCUS_UNSTATABLE`) render as the
     selection name alone, alphabetically. A count of courses is not an amount
     of benefit, so no number is printed beside it.
5. **Health note,** only when D11's count is non-zero:
   `Some of these courses' bonuses could not be matched to Torn's current text and are not counted.`

All text is set through `textContent`.

## Architecture

### Engine: `pathGains(queue, courses)`

A new pure function between `ENGINE START` and `ENGINE END`, beside
`focusTotals`. `tests/purity.test.js` already enforces that section.

Input: the ordered queue (`number[]`) and the course `Map`.
Output:

```js
{
  courseCount: number,
  degreeCount: number,              // queued courses with tier === 3
  workingStats: [{ stat, amount }], // WORKING_STATS order, zero amounts dropped
  categories: [{
    category,
    // percent (amount desc, then selection asc), then flat (same), then count (selection asc)
    gains: [{ selection, unit: 'percent' | 'flat' | 'count', amount }],
  }],                               // FOCUS_CATEGORIES order, empty categories dropped
  unmatched: number,                // D11: stale rows plus unclaimed outcome strings, queued courses only
}
```

Rules:

- **A duplicated queue id counts once.** `loadPlan` dedupes today, but the
  engine does not lean on that.
- **Reuse `focusTotals`; do not re-derive it.** For each `(category,
  selection)` pair, call `focusTotals(focus, courses, notQueued)`, where
  `notQueued` is every catalogue id the queue does not contain. Its
  `remaining` is then exactly what the queue delivers, with `focusTotals`' own
  unit rule and `FOCUS_UNSTATABLE` handling. Codex confirmed this equivalence
  for every unit in today's taxonomy. A zero `remaining` drops the item.
- **Repeated taxonomy rows inherit `focusTotals`' behaviour.** If one course
  carries two rows under the same selection, `focusTotals` *adds* their
  magnitudes. Its comment says the opposite ("counting its magnitude twice
  would overstate"), but no such repeat exists in today's taxonomy, and
  `tests/focus.test.js` fails the day one is added. This spec makes no dedupe
  claim of its own. The comment/code disagreement is a pre-existing defect,
  out of scope here and noted on the PR.
- **Stale rows contribute nothing.** `focusTotals` reads
  `focusRegistry(courses).entries`, so a row whose outcome text Torn changed
  is already absent.
- **`FOCUS_UNSTATABLE` forces `count`.** Rig Overclocking Limit's "up to 30%"
  and "up to 50%" are successive caps, not additive.
- **Unknown or absent input degrades to an empty result, never throws.**

### Model: `buildPanelModel` gains `summaryAvailable`, `summaryReason`, `summaryOpen` and `pathSummary`

- `summaryAvailable` is **exactly** `queue.length > 0 && problems.length === 0`,
  the gate `finishLabel`, `totalLabel` and `consumables` already share. It is
  `false` on every failure model. One gate, so the button's disabled state and
  the finish date cannot disagree.
- `summaryReason` is `null` when available, otherwise one of three ASCII
  strings: no course data (failure model), empty queue, or unmet prerequisites.
- `summaryOpen` is `state.summaryOpen === true && summaryAvailable`.
- `pathSummary` is built **only while `summaryOpen`**, and is `null`
  otherwise. Measured during plan review: `pathGains` over the 115-course
  queue costs about 7 ms against a 12 ms `buildPanelModel` on desktop Node,
  and every click redraws. Its shape is
  `{ headline, finish, workingStats, categories: [{ text, fullText }], healthNote }`.
  `fullText` is `null` when the line has no overflow.
- `errorModel()`, `loadingModel()` and the fetch-failure model carry
  `summaryAvailable: false`, `summaryOpen: false`, `pathSummary: null`. The
  fetch-failure model also carries the no-data `summaryReason`.

### Nav: one button that is not a view target

`renderPanel`'s left group appends the summary button after the `focus` loop
entry, or after `degrees` when focus is hidden. It is not a view target, so it
does not go through `onViewChange`. It is a plain button with:

- class `tes-path-summary-toggle`, plus `tes-path-summary-open` when open
- label `summary`
- `aria-pressed` set to `"true"` or `"false"`
- `disabled`, and `title = model.summaryReason`, when not available
- a click listener that checks `btn.disabled` itself (the established guard
  for fake-document harnesses), then calls `handlers.onSummaryToggle`

The class name avoids `.tes-summary`, which already exists and styles the
`Total queued time` block.

**Known limitation, kept on purpose:** a native disabled button is not
focusable, so its `title` is out of reach by keyboard and touch. The move
buttons and the existing Focus nav entry use the same disabled-plus-title
pattern. Changing it for one control would make the panel inconsistent, so it
is filed as a panel-wide follow-up rather than solved here.

### Handler: `onSummaryToggle` and the closing wrapper

In `init()`:

- `let summaryOpen = false;` beside `resetArmed`, and a `drawCount` that
  `draw()` increments on entry.
- `onSummaryToggle` clears `resetArmed` and `presetError` like every other
  handler. When the view is not `schedule`, it sets `view = 'schedule'` and
  `summaryOpen = true`. Otherwise it flips `summaryOpen`. Then it redraws.
- `closesSummary(set, redraw)` wraps the handler object passed to
  `renderPanel`. Every function-valued property except `onSummaryToggle`
  becomes a function that remembers whether the summary was open, sets
  `summaryOpen = false`, calls the original, and then calls `redraw()` **if**
  the summary was open and `drawCount` did not move.

Codex checked the rest of the wrapper's assumptions. No handler is invoked
during rendering, no handler calls another through the handler object, and
`fn.apply(this, arguments)` preserves receivers.

`noopHandlers` gains `onSummaryToggle` as a no-op.

### Style

- **New token `--tes-ink-on-light: #1f1f1f`** in the token block. The style
  test forbids using a background token as text. It is right to, because a
  token named for a surface should not be repurposed as ink. An inverted
  control needs a dark *ink*, so it gets one, named for what it does.
- `.tes-path-summary-toggle`: `background: var(--tm-text); color:
  var(--tes-ink-on-light); border-color: var(--tm-text)`.
- `.tes-path-summary-toggle.tes-path-summary-open`: `background:
  var(--tm-good-text); border-color: var(--tm-good-text)`, same ink.
- `.tes-path-summary-toggle:disabled`: the ordinary button fill (`--tm-hover`)
  with `--tm-muted` text and `cursor: not-allowed`. The panel has no generic
  disabled-button rule to inherit, and a disabled inverted button must not
  look like a live one.
- `.tes-path-summary` (the block): `min-width: 0; overflow-wrap: anywhere`,
  divided from the finish line by a bottom border in `--tm-border-2`. No new
  surface, because the overview outline is already the surface.

Specificity, checked: `#tes-panel .tes-path-summary-toggle` (1,1,0) beats the
later generic `#tes-panel button` (1,0,1).

Contrast is asserted, not assumed: `#1f1f1f` on `#ffffff` is 16.5 and on
`#7ee081` is 10.1. Both clear AA.

Mobile: the nav is already a two-column grid under the PDA breakpoint. Six
buttons (with focus) fill three rows, and five leave one cell empty. No
breakpoint change.

## What does not change

- No arithmetic. `schedule`, `planConsumables`, `orderQueue` and `focusTotals`
  are untouched.
- No storage key, no share-string field, no debug-report field.
- Security surface: no `@match`, `@grant` or `@connect` change.
